## 1. 先理解题目究竟在安排什么

A 题研究的是：一份已经确定的计算工作，怎样分组、交给多个计算核心、安排执行次序，才能尽快全部完成。

题目已经给出哪些操作要执行、每个计算操作的耗时、数据块的大小、操作间的数据依赖。参赛者主要决定三件事：哪些操作归入同一个子图；每个子图交给哪个核心；同一个核心上的子图按什么顺序执行。

题面同时明确：实际神经网络计算数据通常远大于单核缓存容量，因此形成分块的细粒度操作和数据块。本题提供的计算图已经描述这些分块计算的数据流；当前要决定的是给定操作的子图归属、执行核心和顺序，不是重新选择神经网络结构或任意改变原有运算。

“神经网络处理器”说明被调度的硬件背景。题目并没有要求训练一个神经网络、提高识别准确率或计算真实的模型输出。输入 JSON 主要描述工作量与依赖，评估程序据此模拟执行时间。

依据：题面 §1.1—1.3、附录 B.3—B.5。

## 2. 直接按题面认识多核 NPU

| 术语 | 在本题中的含义 |
|---|---|
| NPU | 神经网络处理器；本题的平台由 N 个同构 AI 核心和共享 DDR 构成 |
| AI 核心 / Core | 执行分配给它的子图，拥有自己的计算单元和私有缓存 |
| Cube / PIPE_M | 矩阵计算单元及其执行管道 |
| Vector / PIPE_V | 向量计算单元及其执行管道 |
| L1、UB | 每个核心各自拥有的有限片上存储；实际位置看 tensor 的 pos 字段 |
| DDR | 各核心共享的核外主存，本题中读取与写入共同竞争总带宽 |
| COPY_IN、COPY_OUT | 将数据从 DDR 搬入 L1/UB、从 L1/UB 搬回 DDR |
| 带宽 | 单位时间能够搬运的数据量，本题单位为 bytes/cycle |
| Task | CPU 主控向单个 NPU 核心一次下发并统一调度的最小执行单元，组织方式随场景改变 |

在本题的简化硬件模型中，PIPE_MTE2 负责 DDR → L1/UB 以及 UB → L1；PIPE_MTE3 负责 L1/UB → DDR 以及 L1 → UB。这些路径来自题面 §1.2 与附录 A，不能用其他芯片版本的路径替换。

“同构核心”表示题目中的多个核心配置相同，不表示一个核心内部的所有单元功能相同。一个核心内部有矩阵计算、向量计算和搬运等不同资源。

同一个核心的同一条 Pipe 同时最多执行一个操作；不同 Pipe 在依赖和资源允许时可以并行。因此，“一个核心”不等于“所有操作只能排成一条完全串行的队伍”。例如，当前一批数据已经就绪时，可以在满足容量和管道约束的条件下计算当前批、搬入下一批。

华为官方的 Ascend C 架构说明也区分计算、存储和搬运组件。不过真实架构包含更多存储和执行细节。本题明确不考虑 L0A、L0B、L0C、VReg，且规定了简化的四条 Pipe。实际产品文档用于理解背景，竞赛中的路径与容量按题面执行。[华为官方架构说明](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/programug/Ascendcopdevg/atlas_ascendc_10_0008.html)

## 3. 计算图、张量和操作分别是什么

“张量”可以先理解为一块有结构的数值数据，向量、矩阵都是常见情况。对本题的调度而言，最直接的信息是这块数据有多大、放在哪里、谁生产它、谁使用它。

“操作”是作用于数据的动作，可以是计算，也可以是搬运。一个 Tensor 节点代表数据，一个 Op 节点代表动作；它们不能混为一谈。

原始计算图的边只连接两种不同节点：Tensor → Op 表示输入，Op → Tensor 表示输出。执行器内部展开时可以另外生成资源复用依赖；不要把展开后的执行图与题目原始输入图的定义混淆。

先看原题自己的例子。§1.2 的图 1 以分块矩阵乘法说明：每个数据分块经历“从 DDR 搬入 L1 → 由 Cube 计算 → 将结果写回 DDR”。输入数据、搬运操作、核内数据、计算操作和计算结果，通过箭头连接起来。

这样描述的目的，是同时表达“做什么计算”和“计算需要的数据什么时候能到”。一个计算操作必须等所需输入就绪，才能进入后续资源就绪判定；不同操作是否能够重叠执行，还取决于它们使用的 Pipe 和缓存状态。

附录 B.7 另给出一个最小示例：16 字节数据由 DDR 搬入 UB，执行一次给定耗时为 4 周期的 ADD，再将 16 字节结果搬回 DDR。题面列出的示例结果是 Makespan = 6 cycles、原图与调度后的 COPY 总量均为 32 bytes、新增搬运量为 0。这些数字直接来自原题，不是本次运行得到的成绩。读这个例子时，应先分清数据节点、操作节点以及二者之间的依赖。

“有向无环图”，简称 DAG，强调数据流有方向，且不存在一圈互相等待的依赖。拓扑序就是不把后续操作排到其前驱之前的一种顺序；这样的顺序通常不唯一。

依据：题面 §1.2、附录 B.3。

## 4. “切图”是在分组，原来的计算和依赖仍然存在

切图需要给每个非 COPY_IN/COPY_OUT 操作指定一个子图编号。一个子图可包含多个操作。之后再为每个子图指定核心和同核次序。

可以把三个决定依次读成：

1. 分组：这些操作是否放在同一组？
2. 分配：每一组交给哪个核心？
3. 排序：这个核心先做哪组、后做哪组？

子图数不要求等于核心数。比如 4 个核心可以承担多于 4 个子图，一个核心按规定顺序执行分配到自己的多个子图。

切图并不删除原有依赖。若前后操作被分到不同子图，数据仍然必须传递，评估器会按场景补上需要的搬运。

分组必须使子图依赖图仍然无环；原图无环并不能替代对分组后依赖的检查。每个非 COPY 操作必须恰好归入一个子图，每个子图必须且只能安排到一个核心的序列中，同核顺序不得违反依赖。

“同核顺序”还需按场景理解：场景 A 中独立 Task 按序激活；场景 B 中同核子图合成一个 Task，顺序用于核内排布，随后仍执行多 Pipe 流水。不能额外假设问题 2、3 中存在“前一子图全部操作结束，后一子图才能开始”的统一屏障。依据是附录 C.1、C.3、D.2、D.4。

两类正式输出是 `node_to_subgraph` 和 `core_schedules`。前者记录计算操作属于哪个子图，后者记录每个核心的子图顺序；不要求提交每一个操作的开始时刻。评估器负责展开、核内调度和全局模拟。

依据：题面 §1.3、附录 B.5、D.1；附件 README 的合法性检查说明。

## 5. 为什么平均分配计算量不等于最快

首先，依赖会导致等待。即使某个核心空闲，只要输入尚未产生，它也无法提前执行依赖这些输入的操作。

其次，数据搬运也要时间，而且所有核心共同竞争 DDR 的读写总带宽。本题规定总带宽为 60 bytes/cycle，不是每个核心各有 60，也不是读取和写入各有独立的 60。

附录 D.5 规定，在途 DDR 搬运公平共享这个带宽池；有新搬运加入或已有搬运完成时，评估器会重算完成时刻。因此，搬运耗时与其他核心此刻在做什么有关，不能给每条跨核依赖随意设定一个固定通信时间。

再次，把相互依赖的操作分开可能让中间数据额外出核、进核。数据可能原本能在片上直接接着使用，分开后却需要经 DDR 中转；多个 Task 还可能重复读取同一输入。

但是，合并得越大也不保证越好：可并行的组可能变少，同时需要驻留的数据可能变多，进而引发缓存换出与换入。

最后，操作数量并不代表工作量。不同操作的 cycles 不同、占用的 Pipe 不同、相关数据块大小也不同。两个核心各拿一半节点，并不保证工作量均衡，更不保证全局结束时间最短。

这些是由题面资源规则推导出的理解，不代表已经确定了哪种切图策略更优。对实际用例的优劣最终必须看固定评估程序。

依据：题面 §1.3—1.4、“算法优化方向”、附录 D.5。

## 6. 缓存容量限制的是“同一时刻仍占着空间的数据”

固定配置中，每核 L1 容量为 524288 字节（512 KiB），UB 为 131072 字节（128 KiB）。二者要分别检查，不能合并当作任意数据都能使用的一个大池子。

容量约束不是要求整个用例的所有张量大小之和都能放进缓存。已经用完的数据可以释放空间，后来才要用的数据不必从一开始全部装入；关键是某一时刻同时驻留的数据占多少空间。

附录 C.2 给出了容量不足时的处理规则：从不属于当前操作输入、输出且未来仍会使用的数据中，选择下一次使用最晚者换出。如果 DDR 已有有效副本，不一定需要再写出一次；否则先插入 COPY_OUT，后续需要时再插入 COPY_IN。

缓存压力可能引入额外搬运，其中实际访问 DDR 的部分竞争 DDR 总带宽。问题 3 中命中只读 Cache 的 COPY_IN 使用独立的 Cache 读带宽，不能把所有逻辑搬运都直接当成真实 DDR 流量。题目给出的核内调度程序处理换入换出细节；参赛者的分组和顺序影响哪些数据同时存活，因而影响额外搬运与最终时间。

“多留数据以便复用”有收益，也有占用空间的代价。这是问题 2、3 中尤其重要的矛盾。

依据：题面 §1.2、“算法优化方向”、附录 C.2—C.3。

## 7. 两种同步场景与三个正式问题

请把“A 题”与“A 场景”分开：A 题是整道题，场景 A、场景 B 是其内部的两种硬件抽象。

题面 §1.5 首先以“是否具有核间同步信号传递机制”区分场景。场景 A 没有这一机制，子图间的同步依赖由 CPU 主控通过 Task 调度完成；场景 B 具备核间同步机制，源核心写入 DDR 后发送同步信号，目标核心在满足同步条件后再读取数据。下面的 Task 组织与缓存规则必须放在这个背景下理解。

| 对比项 | 问题 1：场景 A | 问题 2：场景 B | 问题 3：场景 B + L2 |
|---|---|---|---|
| Task 的组织 | 一个子图就是一个 Task | 同一核心的全部子图合并成一个 Task | 同问题 2 |
| 同核不同子图的数据 | 不跨 Task 保留，仍经 DDR 中转 | 可以在 L1/UB 复用，但受容量约束 | 同问题 2 |
| 跨核中间数据 | 经 DDR 中转 | 源核写出、同步、目标核读入 | 保留问题 2 的依赖与同步机制；符合 Cache 查询规则的读入可以命中 Cache |
| 额外资源 | 无题三的共享只读 Cache | 无题三的共享只读 Cache | 增加全核共享的只读 FIFO Cache |
| 要理解的主要权衡 | 并行机会与 Task 边界开销 | 同核复用、跨核并行与缓存占用 | 共享数据能否及时复用、Cache 容量和读带宽 |

问题 1 中，两个相邻子图即使交给同一核心，也不能跨 Task 保留片上数据。因此“同核必然免通信”的常识不能套用到场景 A。题面说同核与跨核单位通信成本相同，指相应的通信方式；不能因此忽略二者不同的等待参数。

问题 1 的 Task 激活要满足多个条件。同核前一 Task 完成后至少等待 100 周期，跨核前驱 Task 完成后至少等待 1000 周期；存在多个约束时按最晚满足的时刻启动，而非把所有等待数字简单相加。

问题 2 允许同核数据复用，但跨核仍需要源端 COPY_OUT、500 周期同步延迟和目标端 COPY_IN。500 周期只是附加等待，不包含数据写出和读入的全部耗时。该等待本身不占用 Pipe 或带宽池。

问题 3 的共享只读 Cache 容量是 1048576 字节（1 MiB；题面写作 1 MB），读带宽为 250 bytes/cycle，与 DDR 带宽池相互独立。只有 COPY_IN 可以查询并命中它；命中走共享 Cache 读带宽，未命中走 DDR。COPY_OUT 不能命中这个只读 Cache。Cache 命中也不取消原有数据依赖、跨核同步等待或对应 Pipe 的占用。

替换规则是 FIFO：先装入的先被淘汰，命中不刷新顺序。它不是 LRU。单个张量大于 Cache 容量时不缓存；不同核心同时读 Cache 也要共享其总读带宽。因而 250/60 只能比较两条资源通路的标称带宽，不能当作整道题的固定加速倍数。

以上数字是赛题模拟参数。时钟周期不等于毫秒，题面未给统一硬件时钟频率时，不应随意换算成现实秒数。

依据：题面 §1.5、问题 1—3、附录 B.4、D.2、D.5；附件 `data/config.txt` 和 `docs/多核并行模拟执行算法.md`。

## 8. 题目最终如何判断“快”

主指标 Makespan 是全部操作结束时刻的最大值，即从任务开始到最后一项工作结束经过的时间。它由多核评估程序在统一时间轴上模拟得到，不能把各核心局部时间简单相加，也不能拿某个子图独占带宽时的参考时间代替。

按题面 §1.4 的定义，题目同时观察新增 DDR 搬运量；问题 3 还观察 Cache 命中率。命中率按命中字节数除以可由 Cache 服务的总访问字节数计算，不是只数“命中了几次”。搬运少、命中高都有解释价值，但不能取代全局完成时间。

这里必须保留一个实现口径说明：当前题三代码的 `data_movement_bytes` 在 Cache 模拟前按 COPY 图和换入换出记录统计，命中时没有扣减。因此该字段不能直接解释为扣除 Cache 命中后的实际 DDR 流量。它与题面“新增 DDR 搬运字节数”的文字定义存在需要注明的差异，具体证据见文末。导读不会为消除差异而自行改题目定义或评估器。

问题 1、2 中，一个用例在 k 核下的加速比是：

\[
S_i(k)=T_i(1)/T_i(k).
\]

单核基准采用题目指定的整图启发式核内调度结果。100 个用例的平均加速比，是先分别算出 100 个比值，再求平均；不能用全部单核时间的总和除以全部多核时间的总和替代。

问题 3 另要求在相同核心数下比较无 L2 与只读 Cache 配置，比例为“无 L2 的 Makespan / 有 Cache 的 Makespan”，它的分母、分子都不是默认的单核基准。

单核基准是固定启发式算法的结果，不是理论最优值。题面脚注明确提醒：多核加速比可能大于核数。因此不能仅凭“4 核超过 4 倍”就断定数据一定错，也不能由此宣称突破某种硬件理论上限。

还要区分两个时间：生成方案花费的现实运行时间，以及方案在模拟器中执行的 Makespan。题面希望单个用例的方案生成能在约 5—10 分钟内完成；它不是要求被模拟的神经网络执行 5—10 分钟。

依据：题面 §1.4、问题 1—3 及脚注。

## 9. 附件里有什么，你们需要做到哪一层

本次只读检查了附件 ZIP，确认有 `case_001.json` 至 `case_100.json` 共 100 个计算图用例，以及固定 `config.txt`、README、核内调度说明、多核模拟说明和 Python 评估程序。

每个计算图主要含三个数组：`tensors` 描述数据位置与字节数；`ops` 描述操作类型、Pipe、cycles；`edges` 描述生产和使用关系。它们是调度用的结构化输入，不是需要逐个读取真实图片或训练标签的数据集。

例如，实际 `case_001.json` 含 200 个 CONV、200 个 RELU、200 个 ADD，以及 201 个 COPY_IN、200 个 COPY_OUT，共 1001 个操作节点。其中需要在切图输出里覆盖的是 600 个非 COPY 操作。这只是在核对文件组成，没有对它们求解。

附件提供的评估器通过 Python 模拟资源和时间。我检查的导入只使用 Python 标准库和包内脚本；理解与运行这套评估流程不以安装 MATLAB 或拥有真实昇腾 NPU 为前提。模拟的“2—5 个核心”指题目平台中的核心，不能直接与笔记本 CPU 的物理核心数等同。

有几项职责边界值得记住：

- cycles、size、pipe 和依赖来自输入，不能为了效果好而自行改值；尤其不能依据操作名字猜测或更换 Pipe。
- DDR COPY 的实际耗时由搬运量与共享带宽决定。即使某个 COPY 的 cycles 字段为 0，也不能据此把搬运当作免费。
- 选手输出分组、分核和顺序；评估器补边界搬运、安排核内执行、插入必要换入换出并模拟全局时间。
- 核内排布的局部参考时间不等于最终多核 Makespan。
- `stub_multicore_cut_and_schedule.py` 是格式示例，README 明确说它不是性能基线。
- 正式实验采用题目给定的全部用例和固定配置；本次导读没有执行这些实验。

## 11. 初学时建议按这个顺序读原题

先把一个操作看清楚：输入数据从哪里来、存在哪里、使用哪个 Pipe、输出被谁使用。再读由几个操作组成的小计算图，识别必须先后的关系与可能并行的分支。随后区分子图、核心、Task 三个概念，对照问题 1、2 的数据传递差异。最后再加入有限缓存、共享带宽和问题 3 的只读 Cache。

你们的管理科学背景有助于理解依赖约束、资源分配和执行顺序，但题目的对象始终是神经网络分块计算在多核 NPU 上的执行。继续阅读时应保留 Tensor、Op、Pipe、Task 和 Core 的区别，不把它们统一改称一般任务而丢失原有机制。

在当前理解阶段，不需要增加新的物理假设。应先分清三层信息：输入图和配置已经给定的内容；切图、分核、顺序这三个待决策内容；评估器自动完成的边界搬运、核内排布、换入换出和全局模拟。

当前最值得建立的判断习惯是：每看到一个“这样可能更快”的说法，就追问它减少了哪种等待或搬运，又可能增加了哪种资源压力；在得到评估结果之前，把它保留为待验证的推断。
