# 2026 华为杯 A 题三问：可复现基线技术稿

本稿是**基线**，用于确认输入、方案格式和官方评测口径，并给进一步优化提供逐例对照。结果只采用题目附件的原始评测器。它不是最优性证明，也不把 MAGIS 或 Timeloop 的模型数值当作赛题成绩。正式题意以当前目录的《通用神经网络处理器下的多核调度问题.docx》为准。

## 共同问题与原始配置

给定每个用例的计算图，非 COPY 操作、依赖和周期均保持原样。允许的决策是把非 COPY 操作划为子图、分配到若干核心，并指定各核心的子图顺序；每问按其正式场景和附件的配置评测模拟执行时间。不能把不同评测器的周期数或真实电脑运行秒数混用。

附件 `data/config.txt` 给出 L1 524288 bytes、UB 131072 bytes、DDR 60 bytes/cycle；问题 1 的跨核/同核 Task 等待分别为 1000/100 cycles，问题 2/3 的跨核 COPY 等待为 500 cycles；问题 3 的只读 L2 Cache 为 1048576 bytes、250 bytes/cycle。这里不改配置，也不假设本机 GPU 就是题目中的处理器。

## 一版确定性方案

先扫描原图的非 COPY 操作，沿直接相连的计算依赖，以及同一个 COPY 节点连接的计算生产者和消费者，构造若干弱连通分量。把每个分量视作不可拆任务；它在 PIPE_M 和 PIPE_V 上的周期和分别记为 $w_M$、$w_V$。按 $\max(w_M,w_V)$ 从大到小排序，每次把分量交给加入后 $\max(L_M+w_M,L_V+w_V)$ 最小的核心，平局按已有负载与核心编号确定。全部决策只用输入图，不读取评测结果，因此重复执行得到同一方案。

每个使用到的核心只形成一个子图，并在 `core_schedules` 中安排该子图。这样避免人工制造过多 Task 边界，格式上只输出题目允许的 `node_to_subgraph` 和 `core_schedules`。它是**负载贪心近似**：两条 Pipe 的周期和只是选核权重，不冒充官方 Makespan，也不能保证原图最佳切分。若原图主要是一大块相连计算，它会集中在单核，结果可能没有并行加速。

三个场景使用同一算法生成对应核心数方案，便于得到第一版可比的正确性基线。问题 1 用 `evaluate_scene_a`；问题 2 用 `evaluate_scene_b`；问题 3 用 `evaluate_problem_3`。问题 3 与问题 2在同用例、同核心数上使用**完全相同的方案**，因此两次模拟之差可用于描述该方案下 Cache 的影响；没有为了 Cache 再搜索新的方案。

## 指标与验证

每个用例先用 `singlecore_evaluate.py` 的整图计划得到固定 $T_{1,i}$。问题 1、2 的核数 $n=2,3,4,5$，逐例加速比分别为 $T_{1,i}/T_{1,i,n}^{(1)}$ 和 $T_{1,i}/T_{1,i,n}^{(2)}$。问题 3 的核数 $n=1,2,3,4,5$，在同一方案上计算无 L2 场景 B 与有 L2 场景的比 $T_{i,n}^{(2)}/T_{i,n}^{(3)}$。所有平均加速比都先计算每例比值，再对 100 例作算术平均；不使用平均时间之比。

逐例保存方案 JSON、原始评测器返回的压缩 JSON 和 `summary.csv`。题三 `data_movement_bytes` 是 Cache 模拟前的计划搬运字节，不能称为实际 DDR 总字节；命中情况读取独立的 `cache_stats`，其中 `hit_rate` 为字节命中率。发生评测错误时保存错误文本并可中断后续跑，不用估计值填表。

## 结果与可解释边界

100 个用例的 1500 组评测全部完成。独立复核逐份解压并解析了 1500 份评测 JSON，对照了 Makespan、输入用例名，并检查 1400 份方案的计算操作覆盖和核数；[复核记录](final_metrics/verification.json)显示 0 项错误。附件原始评测文件的 114 个 SHA-256 也与解压时的清单完全一致。下表是逐例计算加速比后，对 100 例取算术平均的真实结果：

| 核数 | 问题 1：相对固定单核 | 问题 2：相对固定单核 | 问题 3：同方案 Q2/Q3 |
|---:|---:|---:|---:|
| 1 | — | 1.0000 | 1.0086 |
| 2 | 1.7192 | 1.7192 | 1.0120 |
| 3 | 2.3343 | 2.3343 | 1.0130 |
| 4 | 2.8734 | 2.8734 | 1.0162 |
| 5 | 3.3249 | 3.3251 | 1.0204 |

数值及未四舍五入版本见 [汇总 JSON](final_metrics/aggregate.json)，500 行逐例核数数据见 [CSV](final_metrics/per_case_metrics.csv)，图见 [PNG](final_metrics/mean_speedup.png) 与 [PDF](final_metrics/mean_speedup.pdf)。Q1/Q2 在 2–4 核的 100 例中周期完全相同，5 核有 99 例相同；这是**此方案**每核只放一个子图且尽量避免跨核依赖时的实测现象，不能推论两个正式场景一般等价。5 核时有 16 例 Q1 没有快于单核，说明不拆大分量的保守基线在这些图上没有发挥并行性。

Q3 的 5 核 Cache 平均加速比为 1.0204，100 例中 34 例更快、65 例相同、1 例略慢。略慢的 `case_030` 是 561192 对 561199 cycles，相差 7 cycles；不能声称 Cache 对每例都单调改善。5 核下逐例字节命中率的算术平均约为 16.64%，它不等于周期节省比例。图中的 Q1/Q2 曲线高度重合是数据事实，绘图使用空心圆和小方块分别表示。

基线的主要目的在于证明方案合法、输出可复现，并量出不同图结构对多核加速和缓存受益的影响。若继续优化，应优先研究大连通分量的合法拆分与 Task/缓存代价，再用同一原始评测器验证。原始 `baseline_results/summary.csv` 中保留一次试跑时的输出目录错误行，紧随其后的同组合成功行才是本次结果；汇总脚本按最新成功记录整理完整矩阵。
